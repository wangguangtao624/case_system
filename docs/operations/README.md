## 4. Codex 每个任务怎么做

1. 读取 AGENTS.md、ops/AGENTS.md、本手册和任务记录，确认环境与当前提交。
2. 新任务在 38 的功能分支进行；一个主要任务一次推进，不在生产目录开发。
3. 写下业务目标、改动范围、验收操作、数据兼容策略。
4. 实现后检查差异；执行类型检查、lint、相关业务测试和构建。
5. 在独立预发布目录部署固定版本，进行浏览器与权限验证。
6. 报告预览方式、提交号、通过与未通过的项目、是否变更数据库。
7. 用户反馈后继续修改、重验；用户明确验收后才能进入未来功能的生产发布。
8. 把最终决定和证据保存到任务、验证、发布记录，聊天不是唯一记录。

有多项未来任务时，先建立 docs/tasks/<编号>.md 与 docs/roadmap.md；不要把聊天里的想法直接当作已验收功能。

## 5. 检查与构建

在 38 的候选版本目录运行 `bash ops/validate-release.sh`。
脚本检查主机 IP、干净工作区、测试数据库、独占构建锁；使用冻结锁文件安装依赖；
执行 tsc、lint、运维恢复测试、Next 构建和服务端打包。任意一步失败即停止。
结果保存到 `~/case-system/validation/<commit>/`。
业务测试由任务决定，例如现有 `pnpm exec tsx --test tests/tree-loader.test.ts`。
类型检查与构建成功不代表业务正确；登录、权限、保存、并发修改、附件、统计都要覆盖。
历史 lint 错误不能忽略为“通过”，也不应为运维任务随意重写业务代码；记录并另开修复任务。

代码合并后若提交号变化，需要重新确定发布版本和验证证据。
用户验收的构建产物进入生产，不在生产随意 pnpm install 或重新构建。
待发布产物至少含 .next（不含 cache）、dist、public、运行依赖和版本清单；
Node/架构/系统版本匹配。记录产物 SHA-256 与源代码提交。

## 6. 备份：每小时执行，远端验证后才算成功

12 的 crontab 在每小时第 7 分钟运行备份，使用低 CPU/磁盘调度优先级。
步骤：SQLite 在线 Backup API 生成快照 → 复制附件与必要配置 →
记录表行数和文件 SHA-256 → 本地 SQLite/引用校验 →
SSH/rsync 上传到 38 的 .partial-* 目录 → 远端重新校验 → 改名并更新 latest。
失败不会把不完整目录提升为 latest；错误会进入监控。
传输没有 --delete，也不使用 --inplace；历史快照可使用硬链接节省不变附件的空间。

本地保留最近 6 份成功快照；38 保留最近 48 份以及最近 30 天每日一份。
仅清理由工具生成且已验证的完整快照；.partial-* 不自动当作成功备份或清理目标。
故障遗留的 partial 由 Codex 核对后清理，避免盲删。

覆盖 SQLite、uploads、data/bug-feedback、本地 JWT 密钥及存在的 .env 配置。
密钥和生产配置只在受保护的备份内；测试恢复不复制它们。
如果以后增加外部存储、其他附件目录或数据服务，必须同步更新备份范围。

在线数据库快照是一致的，但附件复制不是整个文件系统的同一时刻快照。
工具核对数据库引用的附件存在，并对复制结果计算校验和；并发删除导致缺件会失败报警。
要发布破坏性迁移或要求严格一致恢复点时，安排短暂停写并做最终备份，不能声称零风险。

计划数据丢失窗口约 1 小时，实际取决于“最近成功备份”，不是定时器是否触发。
超过 2 小时未验证即告警。恢复时间以后续演练实测为准，不承诺未经验证的分钟数。
12 和 38 同一内网，两机备份不覆盖共同故障；后续增加独立离线/异地副本。

## 7. 恢复和测试数据

恢复脚本只允许新的非生产目标目录，拒绝覆盖已有目录。
先验证数据库、行数、SHA-256 与附件引用，再复制数据库和附件，改写副本中的绝对路径。
清除 active_sessions、生成独立 JWT 密钥，不导入生产环境变量。
副本仍包含真实业务信息和用户密码哈希，并非脱敏数据；只在受限环境使用。
初始测试入口绑定 loopback，通过 SSH 隧道访问，不直接公开。
需要向更多人开放预发布时，先制作脱敏数据和独立测试账号，再安排访问控制。

38 的系统 timer 每月 1 日北京时间 03:00 自动做数据库与附件恢复演练，保留最近两份演练副本。
数据库字段/存储路径/附件机制改动后再做一次。完整业务验收仍须单独执行。
验证完整性不等于完整业务演练：还要启动应用、检查登录、历史用例与附件下载。
不要把备份本体当开发数据库，不用硬链接把测试目录接到备份目录。

## 8. 生产发布：Codex 操作，人只验收和决定上线

发布前必须准备：准确提交号、检查报告、用户验收记录、产物校验和、迁移说明、
预计影响窗口、当前生产版本与可恢复的旧程序产物、恢复步骤。
`python3 ops/release-preflight.py --candidate <完整SHA> --report <验证证据目录>`
是只读检查，不会部署。它拒绝生产脏工作区、缺失/不匹配的验收证据和过期备份。

本次发现生产有未提交业务修改，不能覆盖，也不能把远端 main 直接当作当前完整生产源码。
先保留并核对这些修改，在 38 的独立基线分支验证；确定需要保留的业务修改后再归入正式版本。

未来一次发布的执行顺序：
1. 在 38 测试并验收该版本，整理产物和证据，确认 main 合并策略（只允许可核对的版本）。
2. 同步代码到远端仓库，12 只 fetch；检查工作区和当前进程，禁止直接 git pull 覆盖工作。
3. 立即执行一次备份，确认 38 上的验证时间及完整性，保存旧程序构建产物。
4. 根据变更决定是否停写，受控停止现有服务；迁移在维护窗口内只执行一次，记录结果。
5. 更新准确代码版本和已经验收的构建产物；data、uploads、密钥、生产配置保持原位。
6. 使用既有 service-manager.sh 启动并验证 HTTP、登录、只读业务及经授权的写入场景。
7. 观察日志和监控，保存发布记录和回退版本；再结束维护窗口。

这份手册刻意不提供会把开发目录整包覆盖到生产的“一键同步”命令。
Codex 可以按这些步骤完成实际发布，用户不需要手工执行；当前没有待验收的新功能要发布。
将来需要无人值守发布时，先把版本化产物与迁移机制进一步自动化并演练。

## 9. 故障处理

页面异常但数据兼容：回退程序和静态资源。服务崩溃：当前 supervisor 按既有退避机制重试。
数据库迁移失败：保持维护状态，按迁移事务和恢复方案处理。
已有错误业务写入：先限制相关写入，再评估修复，不能自动用旧数据库覆盖。
恢复旧数据库可能丢失新数据，程序回退不等于数据库恢复。
38 故障：12 继续服务，备份超时报警；不要把这套架构称为自动高可用。
12 故障：38 独立监控仍可用；是否人工切换生产需要数据校验、写入唯一性和入口切换方案。

## 10. 实时监控的真实覆盖范围

12：crontab 每分钟采集、每分钟检查面板进程；面板只监听 127.0.0.1:8765。
38：systemd 系统级 timer 每分钟采集，独立于开发账号和 Codex 聊天；面板同样为 loopback:8765。
38 通过只能执行 metrics 的受限 SSH key 读取 12 指标，不能借此执行任意命令或修改生产。
采集：内存可用量、Swap、PSI、磁盘、负载、HTTP、远端备份验证时间、最近故障变化。
告警：HTTP 连续 3 次失败、可用内存低于 20% 持续 10 次采样、磁盘超过 80%、
备份超过 2 小时或失败、跨机采集失败。面板数据超过 3 分钟自动标识过期。
页面每 15 秒刷新；服务器采样仍为约 1 分钟。它不是逐秒业务 APM。

在你自己的电脑建立隧道：
`ssh -N -L 8765:127.0.0.1:8765 wangguangtao@10.26.10.38`
然后浏览器访问 http://127.0.0.1:8765。12 出问题仍可查看 38 面板。
查看预发布：`ssh -N -L 5001:127.0.0.1:5001 wangguangtao@10.26.10.38`。

告警目前记录在面板与事件文件，不等于主动通知。尚无指定的企业微信/钉钉/飞书/邮件 Webhook，
也没有可用的 Codex 定时唤醒工具，因此没有声称已经启用聊天主动报警或 AI 全天候在线。
提供通知渠道后，Codex 可接入故障/恢复通知；无变化时保持安静。

## 12. 文件与凭据

12→38 专用运维私钥只在 12；开发机不复制该私钥，也不复制 GitHub 私钥。
38→12 监控 key 的 authorized_keys 绑定来源 IP、强制 metrics 命令、禁用转发。

转发通道不改生产工作目录；38→12 的开发 key 不能执行任意生产命令。
bootstrap-38.sh 中的内容仅为公钥；不含密码。不要把密码写入任务、源码或配置。
