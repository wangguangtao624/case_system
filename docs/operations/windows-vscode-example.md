# Windows + VS Code + Codex：一次功能开发怎样走完

本次确认：个人电脑 10.26.40.167 为 Windows；VS Code 当前连接生产服务器 10.26.10.12。
localhost:52444 从聊天链接打开。12 和 38 均无 52444 服务，38 的监控实际监听 127.0.0.1:8765。
因此缺少的是 Windows 到 38 的本地端口转发，不能把服务器上的 localhost 当成个人电脑的 localhost。
服务器到 167 的 SSH 连接超时，当前无法远程替 Windows 建立监听；这不证明 Windows 没有其他本地服务。

## 1. 先让 Windows 能看见网页

在当前 VS Code 文件树找到 ops/client/connect-windows.cmd，右键下载到 Windows，双击运行。
该脚本必须在 Windows 执行。Remote-SSH 窗口内的集成终端实际运行在服务器，不能替代 Windows 本地终端。
脚本使用 Windows 的 ssh.exe，不保存密码，不修改服务器或全局 SSH 配置。
完成 SSH 认证后保持窗口打开，浏览器访问：

|Windows 本地地址|实际目标|用途|
|---|---|---|
|http://localhost:52444|38 的 127.0.0.1:8765|监控|
|http://localhost:5001|38 的 127.0.0.1:5001|固定预发布版本|
|http://localhost:5002|38 的 127.0.0.1:5002|正在开发的页面，开发服务运行时才可用|

如 localhost 解析有差异，可用 127.0.0.1 代替。若端口已占用，SSH 会报错停止，不会杀掉原进程。
如果 Windows 有 VS Code 自动转发的同名端口，先识别它，再选择只保留一种转发方式。
关闭脚本窗口只断开观看通道，不会停止备份、监控或预发布服务。
等效的 Windows PowerShell 命令：

```powershell
ssh -N -T -o ExitOnForwardFailure=yes -L 127.0.0.1:52444:127.0.0.1:8765 -L 127.0.0.1:5001:127.0.0.1:5001 -L 127.0.0.1:5002:127.0.0.1:5002 wangguangtao@10.26.10.38
```

本次已用相同的监控映射在服务器侧建立临时隧道并测试；Windows 端尚需用户或本地 Codex 运行一次。

## 2. 保持你熟悉的 VS Code 工作方式

保留连接 12 的窗口做生产运维；新开一个窗口，使用 Remote-SSH: Connect to Host，连接 wangguangtao@10.26.10.38。
打开 /home/wangguangtao/case-system/workspaces/main，确认左下角远程主机是 38。
在该窗口使用 Codex 插件，让它先报告 IP、工作目录与分支。
不强制某个扩展运行位置；按该扩展的远程安装与登录要求配置，在 38 的工作区中验证执行主机。

你仍然可以用源代码管理查看未提交差异，用提交记录/分支比较查看已经提交的修改。
AI 提交后“更改”列表为空不表示没有修改，提交中仍保留完整差异。
VS Code 连接哪台主机，远程文件编辑和集成终端就作用在哪台机器。

## 3. 以新增“用例变更历史”面板为例

这是流程示例，本次没有开发该功能。

### 第一步：你说明业务目标

对 38 的 Codex 说：

> 新增用例变更历史，记录谁在何时修改了哪些字段。历史查询权限与原用例一致。
> 先确认验收标准与旧数据兼容方式，再在 38 开发、测试并部署预发布，不发布 12。
> 开始时报告执行主机、目录、分支；完成时报告代码差异、检查结果和预览地址。

Codex 记录任务，检查现有保存与权限机制，从确认的基线创建 feature/case-history 分支。
当前基线还有原有未提交业务修改和 16 项 lint 错误，先整理基线，不能跳过必需检查直接上线。

### 第二步：在开发区修改和验证

开发目录是 ~/case-system/workspaces/main，使用开发数据库与附件副本。
Codex 修改 UI、接口和迁移，必要时启动 loopback:5002 的开发服务。
你看代码差异、浏览器效果并提出调整。开发区允许频繁重启和试错。

历史记录的示例兼容方案：新增历史表，保留原用例与附件。旧用例从功能启用后开始记录，
无法凭空补出从前没有记录的修改。迁移需有版本与验证记录；现有初始化逻辑不能替代完整迁移设计。

测试至少覆盖：保存一次形成正确记录；无权限用户读不到历史；失败或冲突保存不生成假记录；
旧用例与附件仍可访问；归档规则保持正确。

### 第三步：构建并交到预发布

Codex 执行类型检查、lint、相关测试和构建。失败则修复并重验。
固定通过检查的代码与构建产物，把候选版本放到独立预发布目录，使用自己的测试数据库与附件。
预发布是固定候选版本，开发区再编辑文件不会自动改掉你正在验收的页面。
初始测试数据来自生产备份的隔离副本，包含真实业务信息，并非已脱敏数据。

### 第四步：你在 5001 端口验收

你登录独立测试账号，修改一条测试用例并查看历史，再验证权限和附件。
这些操作只改变预发布副本，不改变生产或受保护的备份。
有问题就回到开发区修复、重新构建和部署候选版本；不能直接在候选目录补丁后仍沿用旧验证记录。

### 第五步：Codex 按已验收版本发布

你明确验收后，Codex 整理准确版本、构建产物、迁移、影响窗口及恢复方案。
代码经 GitHub 开发分支进入受控合并流程，开发账号的 Git 通道不能直接推 main。
发布前对 12 做新备份并在 38 验证，保存旧程序产物；检查生产工作区与数据兼容。
按需要安排短暂停写，执行迁移与部署，再验证服务、登录、旧用例与新功能。

只合并代码与迁移，不把开发/预发布数据库覆盖到生产。
生产在开发期间新增的数据仍留在 12；如果代码回退，先判断数据库是否兼容。
恢复旧数据库可能丢失新写入，所以不能设置成发布失败就无条件恢复数据库。

## 4. 开发、预发布、备份分别是什么

|区域|供谁使用|变化方式|数据|
|---|---|---|---|
|开发|Codex 与开发者|频繁修改、重启|独立测试副本，可试错|
|预发布|你验收候选版本|按明确版本更新|另一份独立测试副本|
|备份|运维与恢复工具|由备份任务生成并保留历史|生产快照，开发账号不可读写|
|生产|正式用户|受控发布|唯一正式业务数据|

## 5. 备份实际占用什么资源

本次测量：38 总内存约 9.7 GiB，可用约 9.0 GiB；监控服务约 11 MiB，预发布约 110 MiB。
重新校验最新备份的 Python 单进程峰值 RSS 约 26.45 MiB，用时 12.75 秒。
这是校验单进程的测量，不是整个备份流水线的峰值。

附件计算 SHA-256 时每次读取 1 MiB，不会把约 3.5 GiB 的附件全部装入 Python 内存。
Linux 会缓存读过的文件，本次 buff/cache 约 8.5 GiB；多数可回收，不能当成程序常驻内存。
备份会产生 CPU、网络与磁盘 IO，已有低优先级调度、构建串行和资源监控。

两份远端备份合计实际磁盘占用约 3.5 GiB。未改变的附件通过硬链接共用同一份文件内容；
第二份快照新增物理占用约 18 MiB。单独对每份快照运行 du 可能都显示约 3.5 GiB，不能直接相加。
开发与预发布各自的附件副本约 3.5 GiB，保持独立，不用备份文件的硬链接作为可写测试数据。
恢复演练也需要独立磁盘空间。新增附件、替换文件和保留已删除文件的历史会增加磁盘使用，
不是永远固定为 3.5 GiB。保留策略与磁盘 80% 告警共同控制增长。
